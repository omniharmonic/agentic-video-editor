## Setup facts (this episode)
- 4 video files = **2 sessions x 2 angles**: `IMG_0002` + `IMG_0002 2` (117 min, 21 GB each) and `IMG_0003` + `IMG_0003 2` (22 min, 3.6/4.4 GB). 4K HEVC 30 fps.
  The two files of a session share an identical `creation_time` (22:07:45Z and 00:32:47Z), so that is the grouping key. Timecode tracks are NOT usable (`00:00:00:05` vs `00:00:00:20`).
- ONE audio file (`master_audio.wav`, 8437.6 s, 44.1 kHz stereo) exported as a batch across both sessions. Sessions sum to 8346.1 s; the file is 91.5 s longer.
- Drive: ExFAT (writes `._*` AppleDouble files next to every file), ~970 MB/s read, fast enough to edit 4K from.
- The creator's folder convention is `01_PROJECT 02_FOOTAGE 03_AUDIO 04_GFX 05_MUSIC 06_EXPORTS`. The editor must adapt to the creator's layout, not impose its own.

## N1. Sessions: a single audio file can span several takes  (status: applied, T10)
- Assumed: one recording session, one timeline.
- Found: cameras of the same session cluster by `creation_time`; session 2 starts at master time **7119.5 s**, session 1 ends at 7035.3 s, so **84.2 s of dead space** (plus a 4.3 s lead-in and 3.2 s tail) is in the master but on no camera.
  The numbers add up exactly (4.6 + 7030.7 + 84.2 + 1314.9 + 3.2 = 8437.6), which is how to sanity-check "does this audio belong to these videos".
- Change: ingest groups cameras into `sessions`; episode time = the master audio timeline; regions no camera covers are excluded from assemblies; assemblies are produced per session (and combined on request). Session 2 is the "experimental" one: keep it as its own timeline so the creator can decide later.
- Applied: `media.cluster_sessions` (`creation_time` within 120 s + duration within 2 s -> `sessions` in `media.json`, `label` kept across re-ingest), `media.session_report` (recorders, `sum_session_durations`, "may span sessions" warning). `episode.json` cameras carry `session`, `speakers.<id>.cameras` maps session -> camera. `ave plan-cuts [--session]` writes `cutlist.<sid>.json`; `ave assemble [--session|--all-sessions|--combined]` writes the named `assembly.<sid>`; cleanup/final/render/handoff take `--name`. Regions no camera covers are excluded (`regions`/`excluded`), never an error. Verified: the real durations (7030.7/7031.0/1314.9/1315.5 s vs 8437.6 s) cluster into 2 sessions and report a 91.1 s difference (`tests/test_sessions.py`); the synthetic 2-session episode plans, assembles, cleans and renders per session (`tests/test_session_flow.py`).

## N2. Long offsets broke our sync search  (status: applied, T10)
- Assumed: offsets within +-10 minutes (the search window).
- Found: session 2 is 2 hours into the master. A first prototype of a full-length search reported -3366 s: an **FFT wraparound** (lags split at nfft/2, so anything past 5242 s wrapped to negative). Unwrapped it is 7119.5 s.
- Change: coarse search over the whole master on a decimated envelope, with a correct lag mapping (positive lags are k < len(ref), negative are k > nfft - len(sig)), then refine with GCC-PHAT. Add a regression test with an offset larger than half the FFT size.
- Applied: `sync.lag_axis` maps lags exactly (also fixes `gcc_phat`), coarse search is a whole-reference log-energy envelope correlation (`sync.envelope`, `coarse_candidates`), refined by GCC-PHAT at >= 5 points. Regression tests: `test_gcc_phat_recovers_a_lag_beyond_half_the_fft_length` (90 s lag, old code returned a negative number) and `test_sync_pair_finds_an_offset_beyond_half_the_envelope_fft` (350 s). Real validation (`tests/test_sync_real.py`, skipped without the scratch WAVs): session 2 comes out at 7119.413 s and 7118.839 s.

## N3. Camera clocks drift against the recorder, and we only measured it  (status: applied, T10)
- Assumed: one static offset per camera is enough; drift is a warning.
- Found (offset measured at 5 points per take, PSR 100-340 each): s1A **+50 ppm**, s1B +24 ppm, s2A **+85 ppm**, s2B +46 ppm. Over session 1 camera A is **0.33 s (10 frames) off** at the end with a single offset. The tool printed drift and nothing applied it.
- Change: fit offset(t) = a + b*t per camera from several points, store `start_offset` and `drift_ppm` on each source, apply `src_t = (e - a) / (1 + b)` everywhere a source time is derived (EditDoc `source_time`, compile, handoff, cleanup masks). Segments are short, so no retiming is needed, just the right source time per segment. Warn when the linear fit's residual is large (non-linear drift).
- Applied: `sync.json` per file `{start_offset, drift_ppm, psr_min, residual_ms, points[]}`; `editdoc.source_time` is the single formula, used by compile (video position, picture stretch, audio position), handoff, cleanup (`Envelope`, coverage), cutplan, shorts, reframe, review packs. End-to-end proof (`tests/test_drift_e2e.py`): a camera 80 ppm slow with a flash+beep at 689.95 s lands on output frame 30 (expected 30) and the beep at 1.002 s (expected 1.0) with drift applied, and on frame 28 / 0.942 s (55 ms early, 1.65 frames) when ignored. Real data: all four cameras reproduce within 30 ms / 10 ppm (see the test). **New finding:** real clocks wobble 15-50 ms around the fitted line (residual 14-32 ms at 5 points, up to 48 ms at 9), so the residual warning triggers at 35 ms, not 15; and a 1000 ppm clock decorrelates a 60 s PHAT window (the point is retried with a shorter window).
- Lesson for the unit tests: synthetic drift detection passed while the product was wrong. The test that matters is end to end: a drifting camera still lands lips-on-audio at the END of a long take.

## N4. CORRECTED: the master is speaker-per-channel (one host per channel), not "one live channel per session"  (status: applied)
- **First (wrong) inference, from 3 sample minutes:** "session 1 is right-only, session 2 is left-only; fold the live channel to mono". The first real `ave ingest` disproved it: the live channel flipped left/right in 60+ ranges, every 1-5 minutes, across the whole file.
- **What is true (measured):** channels are independent signals (sample correlation -0.08). Against the diarization, **S1 sits on the LEFT channel in 163/165 clear segments (99%); S2 on the RIGHT in 217/217 (100%)**. Each host has their own mic on their own channel; the "dead" channel is just the other person's mic while they are quiet.
- **Consequences:** (1) folding to the "live" channel is WRONG here: it gates each mic on and off and drops interjections. The correct mono is the SUM of both channels (L+R, not the average: the average loses 6 dB). (2) **Speaker identity comes free from the channels** (about 99.5% agreement with pyannote), and it is more robust to overlap and short interjections than any diarizer. (3) Filler/pause cleanup can use each host's own isolated mic. (4) The rendered dialogue must still be dual mono.
- **Lesson (about us, not the footage):** I generalized from 3 samples. The tool's own output on the full file exposed it. Skills must say: classify the channel LAYOUT (speaker-per-channel vs one-dead-channel vs true stereo mix) from the whole file, never from spot checks, and verify against an independent signal (diarization) before choosing a strategy.
- Change: detect `speaker_per_channel` (independent, alternately dominant channels), sum for the dialogue/analysis audio, derive speakers from channels by default for such files, keep the dead-channel fold only for files where one channel is dead and the other is not alternating.
- Applied (T11): `media.classify_layout` decides `channel_layout` (`speaker_per_channel` | `dead_channel` | `stereo_mix` | `mono`) from the WHOLE file (global correlation, per-channel dominance share, alternations; numbers kept in `channel_evidence`). `speaker_per_channel` gets one `channel_map` range `use: "sum"`: `ave audio` writes L+R through `audio.soft_limit` (level kept, never clips), compile folds it to dual mono the same way, `ave transcribe` labels words by the louder mic (S1 = left, S2 = right, `engine.diarization = "channels"`, per-utterance `confidence`), `--check-diarization` reports agreement with the diarizer.
- Verified on the real master (read-only): layout `speaker_per_channel` (corr -0.005, left dominant 42.7% / right 52.3% of loud windows, 158 alternations, 4219 two-second windows); against the scratch diarization, channels agree on 597 of 599 clear segments longer than 3 s (99.67%; 639 such segments, 40 within 6 dB so unclear).

## N6. Handoff at scale: the bridge loses handles on big appends  (status: applied)
- Assumed: one `append_to_timeline` call with every clip is fine (it was for 114 and 219 clips).
- Found: session 1's rough cut has 1221 cuts. One call failed with `stale_handle` (the bridge's object handle expired mid-call), leaving an empty timeline; a 60-clip chunk later failed once with "missing timeline item id" yet the same clips appended fine in smaller chunks (transient, not root-caused).
- Change: appends go in adaptive chunks (halve on failure); after ANY failure the script re-reads how many items actually landed and resumes after them (never double-places); a partial timeline is reused only if it is exactly a prefix of the plan; failures keep the partial timeline and say how to resume. Resolve gates timeline deletion behind a human confirm token, which is correct: we never delete.
- Lesson: my first "cleanup on failure" printed "removed incomplete timeline" while the delete had been refused. Never report an action's success without reading back its result.

## N7. Long turns need a pacing pass  (status: applied, T12)
- Found on the real rough cuts: 62 s average shot in session 1 (hosts take 100+ s turns), 103 holds over the 14 s limit in session 1 and 23 in session 2. Cleanup masks cuts but nothing breaks a long hold. 446 of 752 cuts are masked by a cutaway, which is a lot of cutting away to a listener at cut points while long unbroken stretches remain.
- Change: a pacing pass inserting listener reaction shots at sentence boundaries when a hold exceeds the limit; the interjection rule gets real defaults (speaker-per-channel makes interjections unambiguous); all numbers in policy YAML for the creator to tune.
- Applied (T12): `cleanup.apply_pacing` runs after the masks (`pacing:` in `config/cleanup.default.yaml`, `ave cleanup --no-pacing`): every hold over `max_hold_s` (14) gets 2-4 s reaction shots between words (strong sentence end > pause > word boundary), >= 2.5 s from the neighbouring cuts, on a `role: wide` camera, else the listener's camera (never while they talk), else a 1.10/1.20x punch-in; reason `pacing: reaction`, a confidence each, dialogue untouched, deterministic and idempotent (the real session-2 rough re-run gave identical tracks). `should_cut_to_listener` now reads `config/cutplan.default.yaml` (>= 0.8 s, >= 6 dB over the other mic, shot up >= 6 s, backchannels stay unless >= 1.2 s).
- Measured on COPIES of the real artifacts (replanned with the new interjection policy, then cleaned): **session 2** (1122 s rough): holds over 14 s 23 -> 10, over 18 s 12 -> 0, longest hold 46.9 -> 17.5 s, 15 reaction shots (13 listener, 2 punch-in); **session 1** (6198 s rough): holds over 14 s 103 -> 55, over 18 s 64 -> 1, longest 74.8 -> 18.5 s, 82 reactions (74 listener, 8 punch-in). Every reaction boundary falls between words (0 inside a word) and no listener-camera reaction shows the person while they speak (0 of 74 in session 1, 0 of 13 in session 2; checked against the transcript words).
- **Two findings that change the story.** (1) The 62 s / 33 s "average shot" was the ASSEMBLY. The rough cut was already at 5.1 s average and 11.7 cuts a minute because the cleanup cutaway masks make a cut at nearly every pause cut (442 cutaways in session 1). So pacing cannot bring the average up to 8-12 s; it adds cuts (average 5.1 -> 4.4 s, 11.8 -> 13.7 cuts/min), and the cap `max_cuts_per_min: 8` is already exceeded before pacing runs. The cap therefore guards each insertion (a reaction is skipped in a busy minute) and yields only to a hold already past `max_hold_s + reaction.max_s`; 55 of 82 session-1 reactions needed that override (`rate_override: true`). If the creator finds it too busy, the lever is `masks.*` (cutaway length, `min_hold_s`), and the 55 remaining holds of 14-18 s are the ones the cap refused. (2) One ASR word ("day.") spans 10 s in session 1, so no cut point exists inside that hold (reported as `STILL OVER THE LIMIT`).

## N8. Episodes start with setup chatter  (status: applied, T12)
- Found: the master opens with setup chatter (a spoken slate: take one, we're recording, a few jokes, a mock welcome that the hosts themselves say is not how it starts). The assembly starts at the first camera frame.
- Change: a trim suggestion from the transcript (slate phrases, the real welcome, the sign-off) per session, human-approved, recorded in `episode.json`.
- Applied (T12): `ave trim suggest` scans the first and last 6 minutes of a session for the phrases in `config/trim.default.yaml` (+ `episode.json` `trim_hints`) and prints timestamped evidence and a proposed in/out snapped into a pause, with a confidence; it never applies. `ave trim set` records the human's decision in `episode.json` `trim`, logs it to PROGRESS.md; `ave assemble` honours it (shorter span, still validated); `ave resume` lists an unapproved suggestion as an open question.
- Verified on the real transcript copy (session 1, read-only): slate found at 12.8 s ("take one" phrase), 24.8 s ("recording" phrase), 169 s (a mic-adjustment phrase); the first "Welcome." is at 31.3 s, inside the first 3 minutes, but it is a joke welcome, so it is only taken as the start when no slate talk follows it. Proposed **in 188.90 s** (confidence 0.55): the first sentence of 10+ words after the last slate phrase (it starts at 189.2 s). Proposed **out 7022.84 s** (0.50), the pause before the closing "we're done, let's stop" talk (session 1 ends at 7035.7 s). Session 2 has no slate or sign-off phrases (no proposal, which is right: it starts and ends on speech). With the session-1 trim set, `ave assemble --session s1` gave a 6834 s assembly (7031.6 s before) with `excluded` 0-188.9 s and 7022.84-8437.6 s. ## N10. Review playback of 4K HEVC garbled the audio under load  (status: proposed, W10)
- Reported: the dialogue clip sounded distorted in Resolve, even opened alone. Investigated rather than assumed: the compiled master matches the raw L+R sum (gain 1.000, 1-sample alignment, SNR 41 dB, no block-boundary clicks); six A/B files (raw, float32, PCM24, -6 dB sum, each mic alone) all played clean in a separate test. Cause: playback load (several 4K HEVC streams from an external USB drive, agents running), not the audio.
- Also found while checking: the raw master clips at full scale on loud transients (the L+R sum exceeds 1.0 for about 0.027% of samples); the soft limiter keeps the compiled file under 1.0.
- Change: review proxies (W10). Lesson: when a human reports "it sounds wrong", measure the file objectively first (fidelity vs the source), then isolate by A/B, and only then change code.

## N11. Gain-only loudness normalization clipped the real render  (status: applied)
- Found by the first real proxy render (22 min of 4K): true peak **+1.5 dBTP** against a -1.5 ceiling, with only a warning. Cause: `loudnorm linear=true` reaches -16 LUFS by raising everything; this master has transients about 24 dB above its average (and already clips at full scale in the raw file), so the spikes ended far over full scale.
- Change: a lookahead limiter after the gain stage, and `render` measures the ENCODED file and re-limits harder if the codec overshoots (up to 3 passes). Regression test with synthetic spiky speech (fails before: -0.5 dBTP; passes after) for AAC and MP3.
- Lesson: our fixtures were too polite. Real speech has claps, laughs and clipped peaks. A warning that nobody reads is not a guarantee: verify the delivered file and fix, not just report.

## N12. A -1e-9 s rounding error made the first frame black  (status: applied)

## N16. Clips (and so shorts and content) did not understand per-session edits  (status: applied, T16)
- Found when starting selects on the real project: `ave clips prepare` only loads an unnamed `rough` edit (`list_versions(ep, 'rough')`), but a multi-session episode's cuts are `rough.s1`, `rough.s2`. Captions needed `--stage rough:s2`. Sessions were added (T10) after clips/shorts/captions existed, and only the stages T10 touched learned `--name`.

- Lesson: when a cross-cutting concept (sessions) is added, grep EVERY consumer of the old assumption, and run the real project through every stage, not just the stages that changed.

## N17. A fixed candidate cap silently kept only the first third of a long session  (status: applied)
- Found when choosing clips for the real session 1 (103 minutes): `ave clips prepare` produced 60 windows covering minutes 0-36 and said nothing. Every window scored the same hint (1.0), ties sorted by start time, and a hard cap of 60 kept the earliest. The agent would have picked clips only from the first third without knowing.
- Change: the default cap scales with the edit (about 2 windows per minute, 60-400; 206 for this session); when more windows exist than the cap, survivors are the best window of each time bucket (spread across the whole edit) and the output reports `windows_available`. Regression test reproduces tied hints (fails before, passes after).
- Lesson: any cap or default that was tuned on a 4-minute fixture is a trap on a 100-minute episode; truncation must be spread AND reported.

## N22. What the first real episode taught about the PROCESS (summary of N1-N21)
- Real footage beat fixtures at every stage (sessions, channel layouts, drift, pacing, handoff failure modes, truncation caps). Run the real project through EVERY stage soon after a change, and log the finding the same hour as a regression test.
- Ask the creator for judgment where it is taste (pacing feel, which clips), measure where it is signal (sync, loudness, hold lengths), and never let a default tuned on a fixture decide a long episode.
- The state of the work lives in `PROGRESS.md` and the artifacts on disk; resuming a session by saying "Resume <project>" worked repeatedly.
